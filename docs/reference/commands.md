# Commands, exit codes, bounds and environment

Generated by `just gen-commands` from `muster schema --format markdown`. Do not edit by hand; edit `crates/muster/src/` and run the recipe (CLAUDE.md, invariant 6; ADR 0008). `just lint-commands` fails when this page is stale.

Every command prints one JSON object per line on stdout with Linear's own field names, nested as Linear nests them, and exits 0. On failure it prints one error object on stderr, `{"error": {"code", "exit", "message", "hint", "docs", "linear": {"code", "message", "requestId"}}}`, and exits with the code below. `--human` renders the same data as text. Nothing prompts, pages or colours.

## Global flags

| Flag | Value | Meaning |
| --- | --- | --- |
| `--human` |  | Render the answer as text for a person; one JSON object per line is the default |
| `--trace` |  | Print every request and answer to stderr; the key is never printed |
| `--team` | `<KEY>` | The team key (APP); else MUSTER_TEAM; else the workspace's only team |

## Commands

### muster whoami

Who the key belongs to, the workspace, the team muster will use, and checks on what was read.

No arguments beyond the global flags.

The workspace's settings, its security and auth settings, its counts and its subscription, as Linear returns them.

## Exit codes

The table is append-only (ADR 0008). `0` is success; `2` is also what `clap` returns for a command line it cannot parse.

| Exit | Code | Meaning | What to do |
| --- | --- | --- | --- |
| 0 | `ok` | the operation happened in Linear and the output is Linear's answer | nothing |
| 1 | `failed` | muster's own failure, or an answer from Linear it does not understand | read the message; run again with --trace and report the request and the answer as an issue on this repository |
| 2 | `usage` | the command line cannot be acted on: an unknown flag, a missing value, a --limit over the cap, a team that must be named | read the message; `muster <command> --help` and `muster schema` list every flag |
| 3 | `authentication` | no key was found, or Linear refused it (HTTP 401, AUTHENTICATION_ERROR) | put a Linear API key in LINEAR_API_KEY or in ~/.config/muster/key (docs/reference/commands.md#the-key); `muster whoami` says which source was read |
| 4 | `not_found` | no such issue, team, state, label, project or user (Linear's "Entity not found", or no match for a number, a title or a name) | check the name or identifier; `muster team list`, `state list`, `label list`, `project list`, `user list` and `issue list --search` show what exists |
| 5 | `rate_limited` | Linear's rate limit; the request was not served (HTTP 429 or RATELIMITED); the message carries the reset time | wait until the reset time in the message, then run the command again; muster never waits for you |
| 6 | `refused` | the input was refused: Linear's validation (INPUT_ERROR), a body over BODY_MAX_BYTES, or a muster guard such as a duplicate title | fix the input the message names; for a duplicate title pass --allow-duplicate if a second issue is wanted |
| 7 | `network` | the request was not sent (name resolution, connection, TLS, a timeout before sending), or a query's answer never came; nothing changed in Linear | check the network and MUSTER_ENDPOINT; the command can be run again as it is |
| 8 | `unknown` | a mutation was sent and no answer came: the request may have landed; check before repeating it | read the issue back (`muster issue get`, `issue list --search`) before running the mutation again |

## Notices

A notice is one JSON object on stderr, `{"notice": {"code", "message", "hint"}}`, written while the command exits 0.

| Code | Meaning |
| --- | --- |
| `truncated` | a list was cut at its --limit, or an issue's comments, attachments or sub-issues at their bound; the printed items are complete, there are more |
| `skipped` | `fixtures` found no issue to record `IssueById` on, so that file was not written |
| `partial` | `fixtures` recorded `IssueById` on an issue that lacks comments, attachments or sub-issues, so that node shape is not in the fixture |

## Bounds

Every limit muster has, from `crates/muster/src/bounds.rs` (CLAUDE.md, invariant 3). Nothing is retried, nothing sleeps.

| Name | Value | Unit | Meaning |
| --- | --- | --- | --- |
| `PAGE_SIZE` | 50 | items | the default --limit of every list command |
| `PAGE_CAP` | 250 | items | the largest --limit a list accepts, which is Linear's largest page; a larger value is a usage error, exit 2; a list cut at its limit writes a `truncated` notice to stderr and exits 0 |
| `COMMENTS_PER_ISSUE` | 100 | items | the comments `issue get` fetches with an issue, newest first, as Linear orders them; a longer thread writes a `truncated` notice to stderr and the oldest are the ones left out |
| `ATTACHMENTS_PER_ISSUE` | 50 | items | the attachments `issue get` fetches with an issue, newest first, as Linear orders them; an issue with more writes a `truncated` notice to stderr and the oldest are the ones left out |
| `CHILDREN_PER_ISSUE` | 50 | items | the sub-issues `issue get` fetches with an issue, newest first, as Linear orders them; a parent with more writes a `truncated` notice to stderr and the oldest are the ones left out |
| `TEAMS_PER_PROJECT` | 10 | items | the teams `project list` and `project create` print with a project under `teams.nodes`; `project list` writes a `truncated` notice to stderr for a project in more, and a project `project create` makes has the one team, so it is never cut; bounded so that a page of PAGE_CAP projects stays inside Linear's query-complexity limit of 10,000 |
| `MEMBERS_PER_PROJECT` | 50 | items | the members `project get` prints with a project under `members.nodes`; a project with more writes a `truncated` notice to stderr, and `project update --add-member` or `--remove-member` on it is refused, exit 6, before any request, since Linear replaces the whole member list and muster could not read it whole |
| `MILESTONES_PER_PROJECT` | 50 | items | the milestones `project get` prints with a project under `projectMilestones.nodes`; a project with more writes a `truncated` notice to stderr |
| `PROJECTS_PER_INITIATIVE` | 50 | items | the projects `initiative get` prints with an initiative under `projects.nodes`; an initiative with more writes a `truncated` notice to stderr |
| `REQUEST_TIMEOUT_SECS` | 30 | seconds | one request, connect to last byte; past it a query exits 7 and a mutation exits 8 |
| `BODY_MAX_BYTES` | 262144 | bytes | the largest description, comment, title, name, link or subtitle sent; a larger one is refused, exit 6, before any request, and the message names which one it was; Linux refuses one argv string over 128 KiB before muster runs, so from a flag's value the bound is reached only where the OS allows the argument, from a file or stdin everywhere |
| `RESPONSE_MAX_BYTES` | 16777216 | bytes | the largest answer read; a larger one is muster's failure, exit 1 |
| `RETRIES` | 0 | attempts | how many times a failed request is sent again: never; the exit code tells the caller what happened and the caller decides |

## Environment

Every environment variable muster reads, each with the reason its default cannot be right for everyone (CLAUDE.md, invariant 5). Nothing else is configuration; there is no configuration file.

| Variable | Read by | Why not default | `whoami` check |
| --- | --- | --- | --- |
| `LINEAR_API_KEY` | every command that reaches Linear | a key is the one thing muster cannot infer; the environment is where a CI job or a one-off shell puts it, and the file below is where a laptop keeps it | reports `key.source` as `LINEAR_API_KEY` when it was read from here |
| `MUSTER_KEY_FILE` | every command that reaches Linear, when LINEAR_API_KEY is unset | a laptop with several keys, or a runner that mounts a secret at a path of its own; the default path is the XDG one, `~/.config/muster/key` | fails when it names a file that cannot be read |
| `XDG_CONFIG_HOME` | every command that reaches Linear, to find the default key file | the XDG Base Directory specification lets a user move every tool's configuration at once; muster follows it rather than inventing a path | reports `key.path` as the file under it |
| `MUSTER_TEAM` | issue get by number, issue list, issue create (where it wins over the parent's team with --parent), state list, label list, and whoami | a workspace with one team needs nothing; a workspace with several has no default, and this saves `--team` on every call from a checkout that belongs to one team; `--team` wins over it | fails when it names no team of the workspace |
| `MUSTER_ENDPOINT` | every command that reaches Linear | the tests and `just quickstart` point muster at the fake Linear (ADR 0010); nothing else sets it | warns when the endpoint is not Linear's |

## The key

The key is a Linear personal API key (Linear, Settings, Security & access, Personal API keys). It is read, in this order, from `LINEAR_API_KEY`; else from the file `MUSTER_KEY_FILE` names; else from `$XDG_CONFIG_HOME/muster/key` or `~/.config/muster/key`, trimmed of whitespace. It is never a flag, never printed, never in `--trace`, and never in a fixture (ADR 0008). To write the file on a laptop:

```sh
mkdir -p ~/.config/muster && (umask 077; cat > ~/.config/muster/key)   # paste the key, then Ctrl-D
```

`muster whoami` says which source was read and exits 3 when none held a key. The endpoint is `https://api.linear.app/graphql` unless `MUSTER_ENDPOINT` says otherwise, which only the tests and the quickstart do (ADR 0010).
